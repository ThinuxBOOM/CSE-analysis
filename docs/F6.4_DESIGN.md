## 4. Architecture boundary

```
F5 tables (0008) + F3 (0005) + issuer decisions (0007) + report_filings (0004)       authoritative source evidence
        │   read by the F6.4 LOADER (canonical rendering rules, §17.3)
        ▼
F6.3 pure functions (worker/financial_truth, frozen, UNCHANGED)                      no DB, SQL, file, clock, network
        │   typed, deterministic results (dataclasses, content keys, hashes)
        ▼
F6.4 CODEC + WRITER (worker/financial_truth_store, new)                              the only code that knows SQL
        │   atomic, idempotent INSERTs; database guards re-check keys, hashes and completeness
        ▼
PostgreSQL 17: migration 0015 tables (append-only) + views (projections)
        │
        ▼
later layers (F7 features, F8 availability / supersession, forecasting): read only
```

**Rules**
- **B1.** F6.3 is not modified, wrapped or monkeypatched, and nothing is added to `worker/financial_truth/`. Its purity test requires exactly 10 files. F6.4 lives in a new package, `worker/financial_truth_store/`.
- **B2.** F6.4 never re-implements an F6.3 rule. Admission, identity, observation building, run selection and reconciliation are always the F6.3 functions. F6.4 only loads inputs, serialises outputs, stores them, and chooses which already-computed objects to reconcile (§6.5, §9.4).
- **B3.** F6.4 validates only from **persisted** F5 evidence, never from an in-memory F5 result. Every input is then reproducible from the database (§6.6).
- **B4.** No PDF, document text, network, CSE, Gemini, ML, news or UI is involved, and no scheduler integration (it runs as a CLI; wiring it into P3 is a separate phase).
- **B5.** No F8 availability, supersession or as-of policy is implemented. F6.4 stores the fields a later policy needs (§12).

"Authoritative derived evidence" means the immutable record of what the versioned F6 code concluded from the referenced inputs at that time. It is derived, but it is **not** rebuildable in place: a re-derivation writes new rows, and it is never allowed to replace old ones. Projections are views: rebuildable, never written, never authoritative. **F6.4 has no mutable table.**

### 5.2 Conventions (every table)

- **C1. Content keys and hashes.** Stored as `text` holding the lower-case hex SHA-256 exactly as F6.3 produced it, with `CHECK (x ~ '^[0-9a-f]{64}$')`, as `document_sha256` is stored since 0005. They are never recomputed by F6.4 except for verification.
- **C2. Envelopes.** Where F6.3 defines an output hash over a structure, the table stores that exact structure, serialised by F6.3's `canonical.canonical_json` (= F6.1's), in a `text` column (§11.3). The canonical JSON is ASCII-only (`ensure_ascii`), which gives `CHECK (col ~ '^[ -~]+$')`. A guard trigger recomputes `sha256(convert_to(col, 'UTF8'))` and compares it with the stored hash on every insert. The envelope is the byte-exact, authoritative record. The typed columns and the child tables are its queryable decomposition. The database proves that the decomposition equals the envelope exactly before anything commits, and it can never be extended later (§11.6).
- **C3. Numbers.** Unconstrained `numeric` for every Decimal (§13). No `float`, `real` or `double precision` anywhere.
- **C4. Code tuples** (reasons, annotations, roles) are `text[]`. Nested nil forms are `text[]` whose elements are the form's parts joined by `:` (for example `reported_nil:en_dash`, `reported_nil_word:nil`). This is lossless, because the parts are identifiers without `:`.
- **C5. Times.** `timestamptz`, with `recorded_at timestamptz not null default now()` (§12). Never part of a key, a hash or an identity.
- **C6. Protection on every table T1–T16:**
  - `f5_reject_mutation()` BEFORE UPDATE OR DELETE (row) and BEFORE TRUNCATE (statement);
  - guard triggers (§5.4);
  - deferred completeness triggers (§5.5).
- **C7. Privileges.** `REVOKE ALL … FROM PUBLIC` on every table, view and function. Grants are exactly those in §15.

### 5.3 Operational tables (job ledger)

**T10 `financial_f6_jobs`.** One row per F6.4 job attempt, created before any work. Immutable.

```sql
create table financial_f6_jobs (
  job_id uuid primary key default gen_random_uuid(),
  kind text not null,                                   -- validate | reconcile | cleanup
  f5_run_id uuid references financial_extraction_runs(id),      -- kind = validate (one F5 run)
  configuration_id text references financial_reconciliation_configurations(configuration_id), -- kind = reconcile
  scope text not null,                                  -- 'f5_run' | 'all_issuers' | 'issuer:<uuid>' | 'cleanup'
  store_version text not null,                          -- 'f6.store.1'
  code_revision text,                                   -- git commit of the running code (provenance only)
  parameters jsonb not null default '{}'::jsonb,        -- e.g. {"validate_missing": true}
  host text, pid integer, os_user text,
  created_by text not null default session_user,
  started_at timestamptz not null default now(),
  constraint chk_ffj_kind check (kind in ('validate', 'reconcile', 'cleanup')
    and (kind = 'validate') = (f5_run_id is not null)
    and (kind = 'reconcile') = (configuration_id is not null)),
  constraint chk_ffj_params check (jsonb_typeof(parameters) = 'object'),
  constraint chk_ffj_store check (store_version ~ '^f6\.store\.[0-9]+$')
);
```

**T11 `financial_f6_job_events`.** Append-only state history. The latest event is the job's state (V1).

```sql
create table financial_f6_job_events (
  job_id uuid not null references financial_f6_jobs(job_id),
  seq integer not null,
  state text not null,                   -- started | succeeded | already_present | failed | abandoned | refused
  details jsonb not null default '{}'::jsonb,   -- counts; error class + redacted message; chosen runs (§9.4)
  occurred_at timestamptz not null default now(),
  recorded_by text not null default session_user,
  primary key (job_id, seq),
  constraint chk_ffje_state check (state in ('started', 'succeeded', 'already_present', 'failed', 'abandoned',
                                             'refused')),
  constraint chk_ffje_details check (jsonb_typeof(details) = 'object')
);
```

Guard `f6_job_event_guard()`:
- the first event is `seq 1`, `started`;
- each next `seq` is the previous one plus 1;
- `started` occurs once;
- nothing follows a final state (every state except `started` is final).

For a **validate** job, the data rows and the final `succeeded` event are committed in **one** transaction (§18.1), so a durable success is never missing its event, and an event never claims a success that did not commit. A **reconcile** job commits each partition atomically on its own (§9.4) and writes its final event after the last partition. A reconcile job that never got a final event is marked `abandoned` by `cleanup`, and the partitions it committed stay complete and valid (§18.2).

### 5.5 Deferred completeness triggers (CONSTRAINT TRIGGER … AFTER INSERT DEFERRABLE INITIALLY DEFERRED)

These run at COMMIT. Each parses its parent's envelope once and enforces the reconstruction and canonical order of §11.6. A parent row can never commit without exactly the children its envelope describes:

- **`f6_validation_run_complete()` on T1:**
  - T2 reconstructs E1 `candidates` (typed pairs, by `candidate_ordinal`), in F6.1's order;
  - T3 reconstructs E1 `op1` (the `op1_json` copies, by `op1_ordinal`), in F6.3's order, and each `validated_candidate_ids` maps its element's `validated` source keys through T2;
  - the admitted numeric and nil counts equal T2;
  - the count of T5 = `so_count`;
  - the admitted T2 rows = the T6 members of this run's SOs (every admitted candidate is in exactly one SO; F6.3's grouping).
- **`f6_source_observation_complete()` on T5:**
  - T6 reconstructs E3 `members` and T7 reconstructs E3 `comparisons`, both in F6.3's order;
  - `representative_candidate_validation_key` is the member whose source key is E3's `representative_member` (NULL exactly when that is null);
  - E3's `reported`, `normalized_value` and `half_unit` equal that member's (§11.6.4).
- **`f6_reconciliation_record_complete()` on T13:**
  - T14 reconstructs E4 `observations` and T15 reconstructs E4 `comparisons`, both in F6.3's order;
  - the distinct `document_sha256` count = `document_count`;
  - roles: `conflicting` if and only if `state = 'conflicting'`; otherwise exactly one `representative` when `representative_so_key` is set (that SO), and `supporting` for the rest.
- **`f6_batch_complete()` on T12:**
  - T16 reconstructs E6 `results` (typed pairs, by `result_ordinal`), in ef_key order;
  - the count of `appended` = `records_appended` = the number of T13 records whose `batch_id` is this batch.
- **`f6_economic_fact_complete()` on T4:** an SO of `first_validation_run_key` has this `ef_key`. A fact never exists without the observation that first had its identity (F6.2 §6), even when inserted in a later transaction.

**Seal triggers.** Every child table (T2, T3, T5, T6, T7, T13, T14, T15, T16) also has one deferred constraint trigger, `f6_child_seal()`. At COMMIT, it requires the number of children of the row's parent to equal the parent's verified count:
- for T1's children: `candidates_total` (T2), `op1_count` (T3), `so_count` (T5);
- for T5's children: `member_count` (T6), `member_count·(member_count−1)/2` (T7);
- for T12's children: `records_appended` (T13, by `batch_id`), `results_count` (T16);
- for T13's children: `so_count` (T14), `comparison_count` (T15).

So no child can be added in any later transaction (§11.6).

## 6. Validation-run model

### 6.1 What a validation run is

A validation run is one call of F6.3 `admission.validate_run`: F6.1 over every candidate of **one** F5 run, then OP1, then admission, under one F6 version set and one input set. It is persisted with every candidate result, its OP1 records and its diagnostics, together with the SOs, members and economic facts built from it (`observations.build`), in **one transaction** (§18.1).

### 6.2 T1 `financial_validation_runs`

```sql
create table financial_validation_runs (
  validation_run_key text primary key,                 -- F6.3 ValidationRun.key (content key)
  f5_run_id uuid not null references financial_extraction_runs(id),
```

**Notes**
- **Identity.**
  - **Content key:** `validation_run_key`, the F6.3 digest of (versions, F5 run id, `input_hash`).
  - **Natural key:** `uq_fvr_input_set`, meaning the F5 run, the version set, the issuer decision and the publication instant.
  - The F3 classification is fixed by the F5 run (the guard checks equality), so it is not part of the natural key.
  - Given F6.3's determinism and the loader's fixed rendering (§17.3), one natural key maps to exactly one content key. A mismatch is refused by the unique constraint and reported as nondeterminism (§18.2).
- **The run's status** is implicit. A T1 row exists only if the run completed and committed atomically, with no `running` rows. Attempts, failures and refusals are in T10/T11.
- **Counts** come from F6.3: `admission.summarize` gives the candidate and admission counts, `len(ValidationRun.op1)` gives `op1_count`, and the number of SOs `observations.build` returns gives `so_count`. The deferred trigger (§5.5) checks them against the child rows.
- **Not stored:**
  - the F6.1 `RunEvidence`, which is derivable from the decision, the publication date and the F3 row;
  - the input contexts, which are referenced, not duplicated (§6.6).

### 6.5 Multiple validation runs (the F6.3 hand-over question)

**Definitions**
- **Input set** of a validation run: the F5 run, the F6 version set, the issuer decision (`filing_issuer_links.id`, or none) and the publication instant (`report_filings.uploaded_at` by value). The F3 classification is fixed by the F5 run.
- **Rerun:** a validation with an input set that already has a T1 row.
- **Changed input:** any other input set for the same F5 run. Examples:
  - a new issuer decision (a new row in the append-only 0007 table);
  - a changed `uploaded_at` in the mutable F1 row;
  - a different F6 version set.

**Policy**

| # | Question | Rule |
|---|---|---|
| M1 | Are all runs retained? | **Yes, forever.** T1–T7 are append-only. Nothing is overwritten or deleted because a newer run exists. |
| M2 | Reruns vs changed inputs | A rerun has the same natural key, so the same content key. It inserts nothing and is recorded as `already_present` after the stored hashes are verified equal (§18.2). A changed input has a new natural key, so a new T1 row. |
| M3 | Same F5 run under a different F6 version set | A different natural key, so a separate, coexisting validation run. The code implements exactly one version set (F6.3 `IMPLEMENTED`); rows of other version sets can only come from other code versions and are never mixed (M5). A version set with a new identity version also needs a migration that teaches the T4 guard its encoding (§8.3). |
| M4 | The canonical ("current") validation run of an F5 run under a version set | The run whose input set equals the **current input set** (below). |
| M5 | What makes a run eligible for reconciliation | (a) its version set equals the configuration's (F6.3 `ReconciliationConfiguration.versions`); (b) its F5 run is the one the configuration selects for the document (F6.3 `select_runs`, D-6); (c) it is canonical under M4. |
| M6 | Is the selection deterministic? | **Yes.** The current input set is a deterministic function of committed rows; the natural-key constraint allows at most one matching run; the choice never depends on time of day, job order, or which run was recorded last. |
| M7 | How is the choice recorded? | Each reconciliation job event records the (F5 run, validation run) pairs it used (T11 `details`). Every stored reconciliation input points to an SO, which points to exactly one validation run. The choice is thus append-only evidence. |
| M8 | What if no canonical run exists yet? | The reconcile job first creates it through a `validate` job for that F5 run (§9.4 step 2), or refuses. It **never** falls back to a run with other inputs. A canonical run that disappears during the pass (its inputs changed) stops the partition (§9.4 step 4.1). |

**The current input set** of an F5 run `r` under versions `V` (rule `f6.store.1`, a direct application of F6.2 D-1 and D-7):
- **issuer decision:** the highest `filing_issuer_links.id` for `r.cse_filing_id` (0007: "current decision = highest id per filing"), or none if the filing has no decision;
- **publication instant:** `report_filings.uploaded_at` of `r.cse_filing_id` as currently committed (D-7);
- **classification:** `r.classification_id`;
- **versions:** `V`.

This is **not** F8 supersession: it chooses among *our own validations of one F5 run*, never between documents or filings. The as-of variant (the input set as known at a past time T, F6.2 §9.2 Q2) is deliberately **not** implemented (§12.4). The fields it needs are stored.

V2 `financial_validation_run_current` exposes M4:

```sql
create view financial_validation_run_current as
select vr.*
from financial_validation_runs vr
join financial_extraction_runs r on r.id = vr.f5_run_id
join report_filings f on f.cse_filing_id = r.cse_filing_id
left join lateral (select l.id from filing_issuer_links l where l.cse_filing_id = r.cse_filing_id
                   order by l.id desc limit 1) cur on true
where vr.issuer_link_id is not distinct from cur.id
  and vr.publication_uploaded_at is not distinct from f.uploaded_at;
```

### 6.6 Input snapshot, reference and reproduction

Inputs are **referenced, not copied**: the F5 run, its statements, columns, rows and candidates, the F3 classification and the issuer decision are all immutable rows (0007, 0008, 0010 triggers). The one mutable input, the F1 `uploaded_at`, is stored by value.

**Reproduction** (the `verify` command, §17.6):
1. load the referenced rows with the fixed loader (§17.3);
2. rebuild the F6.3 inputs, with the publication instant taken from T1;
3. call `admission.validate_run` under the pinned Decimal context (§17.4);
4. require equality of `validation_run_key`, `input_hash`, `output_hash` and every candidate's and SO's key and hashes.

A mismatch is reported, never repaired.

### 7.4 Rules

- **O1.** An SO belongs to exactly one validation run, and so to one F5 run, filing and document, and to one `ef_key` (`uq_fso_run_fact`; guard). It never spans runs.
- **O2.** The reported representation is copied verbatim from the representative member's F5 row, and the guard compares it column by column. It is never altered. Normalised values sit beside it.
- **O3.** Nil is a first-class kind (`value_kind = 'nil'`, with NULL numeric fields), never 0. A printed `0` is `numeric` with `normalized_value = 0`. `numeric` SQL NULL never means nil by itself: the kind column decides (§13.4).
- **O4.** An internally conflicting SO has no representative and no interval (CHECKs). The disagreeing pairs are in T7.
- **O5.** SOs are never updated. A new validation run creates new SOs; earlier ones remain (F6.2 §5). An `so_key` with different content is refused (§11.2).
- **O6.** T6 and T7 are exactly E3's `members` and `comparisons`, in F6.3's order: same elements, keys, values, nil state, reasons and flags, with nothing missing, extra, duplicated or reversed. No row can be added later. The database enforces this (§11.6).

### 8.2 Rules

- **F1. The identity is exactly f6.identity.1.**
  - The ten fields are held as typed columns, and the key is F6.3's `ef_key`.
  - There is no role, period start, audit status, fiscal label, scale, printed representation, filing, document, run, F5/F6.1 version, runtime timestamp or value.
  - Attribution is part of the concept (§1).
  - `first_validation_run_key` and `first_recorded_at` are provenance, not identity. They record which validation run first produced the identity and when.
- **F2. A fact is inserted if absent** (`ON CONFLICT (ef_key) DO NOTHING`) in the same transaction as the SO that first has its identity (F6.2 §6). It is never updated or deleted.
- **F3. Currency is part of the identity.** The column has no default and no FX. A non-LKR fact is a fact in its own currency. LKR-analysis eligibility is a later consumer rule (F6.2 §6, §8.2), not a stored state.
- **F4. Scopes never merge:** `group`, `company`, `bank` and `unlabelled` are distinct identities (A-5).
- **F5. Values exist only in reconciliation records** (§9).

### 8.3 The database enforces the identity hash (guard `f6_economic_fact_guard`)

For `identity_version = 'f6.identity.1'` the guard builds the canonical ordered JSON of F6.3 `identity.py` from the typed columns:

```
{"identity_version":"<v>","issuer_id":"<issuer_id::text>","concept_key":"<c>","period_kind":"<k>",
 "period_end":"<to_char(period_end,'YYYY-MM-DD')>","duration_months":<n|null>,"scope":"<s>",
 "operations":"<o>","maturity":"<m>","currency":"<ccy>"}
```

It then requires `encode(sha256(convert_to(json, 'UTF8')), 'hex') = ef_key`.

**Why no JSON escaping is needed.** The CHECKs restrict every field to characters that need none:
- enumerations;
- `[a-z0-9_]` for concept keys;
- `[A-Z]{3}` for currency;
- a canonical lower-case uuid;
- an ISO date built with an explicit format, so it does not depend on DateStyle.

The string therefore equals Python's `json.dumps(..., ensure_ascii=True)` output byte for byte.

**Also refused:** a reserved concept (`financial_concepts.status <> 'active'`).

**Only `f6.identity.1`.** The guard knows exactly this encoding, and the T4 CHECK accepts no other identity version. A later identity version needs a new migration (0016+) that adds its encoding to the guard.

**Consequence.** The database refuses any fact whose key is not the frozen identity hash of its own fields. A proxy issuer (for example the corpus test's `proxy:<symbol>`) cannot be stored, because `issuer_id` must be a real `issuers` row.

### 9.3 Partitions and batches: T12 `financial_reconciliation_batches`

**Partitioning.** Reconciliation is partitioned by **issuer**.
- An economic identity includes `issuer_id`, so every fact, and every SO of that fact, belongs to exactly one issuer.
- The context F6.3 needs (the filings of a document, and the other currencies of the same identity in a document) is computed within the partition. This is because identity-without-currency includes the issuer.

A partition pass is **exactly one call** of F6.3 `reconciliation.reconcile(runs, observations, configuration)`. It takes:
- `runs`: every F5 run of the partition's documents;
- `observations`: the SOs of the canonical validation runs (M4) of the selected runs (M5), decoded from their envelopes (§17.5).

Its F6.3 `ReconciliationBatch` is stored as one T12 row.

```sql
create table financial_reconciliation_batches (
  batch_id uuid primary key default gen_random_uuid(),
  job_id uuid not null references financial_f6_jobs(job_id),
  configuration_id text not null references financial_reconciliation_configurations(configuration_id),
  issuer_id uuid not null references issuers(issuer_id),       -- the partition
  sequence integer not null,                                    -- per (configuration, issuer)
  previous_batch_id uuid unique references financial_reconciliation_batches(batch_id),
  partition_input_hash text not null,                           -- §11.4: F6.4 fingerprint of the pass's inputs
  output_hash text not null,                                    -- F6.3 ReconciliationBatch.output_hash
  output_json text not null,                                    -- envelope E6: selection, exclusions, results
  results_count integer not null,
  records_appended integer not null,
  recorded_at timestamptz not null default now(),
  constraint uq_frb_chain unique (configuration_id, issuer_id, sequence),
  constraint chk_frb check (sequence >= 1 and (sequence = 1) = (previous_batch_id is null)
    and results_count >= 0 and records_appended between 0 and results_count
    and partition_input_hash ~ '^[0-9a-f]{64}$' and output_hash ~ '^[0-9a-f]{64}$'
    and output_json ~ '^[ -~]+$')
);
```

A T12 row is inserted only in the transaction that commits the whole partition (§18.1). **Its existence therefore means the partition pass completed.** There is no "running" batch.

### 9.4 The partition pass (job `reconcile`)

The job runs while holding `F6_LOCK_KEY` exclusively (§15.7).

1. **Select runs.** Load the `F5RunRef` of **all** F5 runs, then call F6.3 `select_runs(all_runs, C)`. This gives one F5 run per document (D-6).
2. **Validate what is missing.** For every selected run, find its canonical validation run (M4).
   - If it is absent, create it with a `validate` job for that F5 run (§6.1). That job has its own T10 row (`parameters.parent_job` = this job) and its own events. It runs in this session, under this job's exclusive lock.
   - With `--no-validate`, the job instead ends `refused` and lists the runs.
3. **Group into partitions.** Group the selected runs by the issuer of their canonical validation run's SOs (runs with no SOs contribute nothing). The partition set is:
   - the issuers with SOs now;
   - **plus** issuers whose latest T12 batch for C has `results_count > 0` (they may have lost all facts).
4. **Process each partition** in `issuer_id` order, in its own REPEATABLE READ transaction:
   1. in this snapshot:
      - load every F5 run of the partition's documents and call `select_runs` on them;
      - load the canonical validation run (M4) of each selected run.

      If any selected run has none in this snapshot, roll back and write nothing for the partition. This happens when an F5 run, issuer decision or `uploaded_at` was committed after step 2. The job records the partition as `inputs_changed`, continues with the other partitions and ends `failed`, and a rerun validates and completes it. Otherwise, decode the SOs of those canonical validation runs;
   2. compute `partition_input_hash` (§11.4); if it equals the latest batch's, **skip** (nothing is written);
   3. call F6.3 `reconcile` and get the batch;
   4. insert T12;
   5. for each F6.3 result, take the latest T13 of (`ef_key`, C):
      - if there is none, or its `input_hash` differs: append T13 + T14 + T15 and insert T16 with `appended = true`;
      - otherwise insert T16 with `appended = false`, pointing at the existing latest record;
   6. COMMIT, which runs the deferred completeness checks.
5. **Finish.** Write the final job event with counts and the chosen (F5 run, validation run) pairs (M7).

### 9.7 Rules and projections

- **C1. The append rule** (F6.2 §7): a record is appended only when its `input_hash` differs from the latest record's for (`ef_key`, configuration). The guard enforces the chain.
- **C2. States are exactly** `single_source`, `corroborated` and `conflicting`, plus `value_kind` `numeric` or `nil` when not conflicting. **There is no `nil_reported` state.** Nil facts are `single_source` or `corroborated` with `value_kind = 'nil'`, and nil against numeric (a printed `0` included) is `conflicting`.
- **C3. A conflict stays a conflict.** A conflicting record has no value, interval or representative (CHECKs). Every SO is an input with role `conflicting`, and every disagreeing pair is in T15. The database stores no winner, because no column could hold one.
- **C4. No precedence.** No column, view or function orders facts by recency, audit status, document type, errata, amendment or restatement. Annotations are stored as reported and never read by any selection rule. D-6 run selection chooses only between our own processing runs of **one** document.
- **C5. "Current" is a projection:**
  - **V4** `financial_reconciliation_current`: for each (configuration, issuer), the latest T12 batch by `sequence`, joined to its T16 results and their T13 records. A fact absent from its partition's latest batch is **not current**, for example because the newer selected run no longer produces it. Its history remains. No invented state is ever written.
  - **V3** `financial_reconciliation_designated`: the latest T9 row per purpose.
  - **V5** `financial_fact_state`: V4 restricted to the designated canonical configuration, joined to T4.

  If the designation points to a configuration that has not been reconciled yet, V5 is empty for it. Nothing stale shows through.

  V4 refines F6.2 §7 ("the latest record by sequence"):
  - for every fact in its partition's latest pass, the two are the same record (the T16 guard, and every appending pass is a new latest batch);
  - a fact that the latest pass no longer produces has no current state, rather than showing its last record as if the configuration still selected that evidence.
- **C6. Idempotent passes.** A pass over unchanged inputs writes nothing (§11.4).

### 9.8 "Why does this fact have this state?" (answered from stored rows, without re-running anything)

For a record `r`:
- **Participating observations:** the T14 rows, meaning the SOs with their documents, filings, validation runs and roles.
- **Each SO's value and precision:** from T5 (`normalized_value`, `half_unit`, `precision`, the interval, the reported copy).
- **Every compared pair** and its F6.1 V8 detail (values, half-units, tolerance, difference, `sign_only`): from T15, plus T7 for comparisons inside an SO.
- **The interval:** `interval_low` = the maximum of the SOs' `interval_low`; `interval_high` = the minimum of their `interval_high`.
- **The smallest half-unit:** `min(T5.precision)` over the inputs.
- **The representative, or why there is none:**
  - `representative_so_key`, `representative_candidate_validation_key` and the verbatim reported copy;
  - or `representative_ambiguous` in `annotations`.
- **Why conflicting:** `reasons` (`internal_conflict:<so_key>`, `values_disagree:<a>:<b>`, `nil_vs_numeric:<a>:<b>`) and the annotations.
- **The exact F6.3 object:** envelope E4, whose SHA-256 is `output_hash`.

## 10. Provenance model

**Forward chain** (all by foreign keys). No payload is duplicated except two kinds of copy:
- the verbatim value copies required by F6.2 §5 and §7;
- the §11.6 element copies, which are proven equal to their envelopes.

```
financial_economic_facts (ef_key; issuer -> issuers; concept -> financial_concepts)
  └─ financial_reconciliation_records (ef_key, configuration_id, sequence; batch -> job)
       └─ financial_reconciliation_inputs (so_key, role) ── financial_reconciliation_comparisons (member pairs)
            └─ financial_source_observations (so_key; validation_run_key; f5_run_id; filing; document SHA-256)
                 └─ financial_so_members (candidate_validation_key, candidate_id)
                      └─ financial_candidate_validations (F6.1 + admission, envelope E2)
                           └─ financial_fact_candidates (0008: raw value, page, bbox, F4 cell fields)
                                ├─ financial_statement_rows / _columns / _extracts (0008: the F4-derived structure
                                │    F5 persists: labels, sections, headers, periods, roles, audit, scope, scale, currency)
                                └─ financial_extraction_runs (0008: F4 extractor + word extractor versions,
                                     document SHA-256, F5 versions, raw timestamp snapshot, recorded_at)
                                     ├─ report_document_classifications (0005: F3 type, periods, FYE)
                                     └─ report_filings (0004) ── report_filing_observations (every CSE listing version)
                                          └─ filing_issuer_links (0007: the decision the validation run used, by id)
```

- **P1. Reverse queries are indexed:**
  - candidate → validations: `idx_fcv_candidate`;
  - validation → SO members: `idx_fsm_cv`;
  - SO → records: `idx_fri_so`;
  - document → SOs: `idx_fso_document`;
  - filing → validation runs: `idx_fvr_filing`.
- **P2. The F4 layer.**
  - Today the F4 link is F5's persisted F4-derived structure and cell fields (page, bbox, F4 status, confidence, cross-check).
  - The member's (`f5_run_id`, `statement_index`, `row_index`, `column_index`, `value_ordinal`) **is** the F6.2 §10 F4 cell key.
  - When the full F4 layer is persisted (a separate phase), it joins on that key with no F6.4 change.
- **P3. Documents are identified by SHA-256 only.** PDFs, document text and page images are never stored (Master Architecture §7.3; F6.2 §11).
- **P4. V6 `financial_fact_provenance`** is a convenience view over the chain above, from a current fact down to the filing. It is not authoritative.

## 11. Identity/idempotency

### 11.1 Keys

| Object | Key | Produced by | Enforced by |
|---|---|---|---|
| Validation run | `validation_run_key` (content) + `uq_fvr_input_set` (natural) | F6.3 | PK; unique; guard; **key recomputed by the database** (§11.6.5) |
| Candidate validation | `candidate_validation_key` (content); (`validation_run_key`, `candidate_id`) (natural); position `candidate_ordinal` | F6.3 | PK; unique; guard; **key recomputed** (§11.6.5) |
| OP1 record | (`validation_run_key`, `op1_key`); position `op1_ordinal` | F6.3 key, scoped by F6.4 | PK; unique; **key recomputed** (§11.6.5) |
| Economic fact | `ef_key` (content = identity) | F6.3 `f6.identity.1` | PK; **hash recomputed by the database** (§8.3) |
| Source observation | `so_key` (content); (`validation_run_key`, `ef_key`) (natural) | F6.3 | PK; unique; envelope hash; **key recomputed** (§11.6.5) |
| SO member, member pair, observation reference, cross-SO pair, batch result | (parent, member / pair / SO / fact) + position (parent, ordinal) | F6.3 membership and order | PK; unique; composite FKs; exact decomposition of the parent envelope (§11.6) |
| Configuration | `configuration_id` (content) | F6.3 | PK; envelope hash |
| Reconciliation record | `record_id` (surrogate) + (`ef_key`, `configuration_id`, `sequence`) + `input_hash`/`output_hash` (content) | database identity; F6.3 hashes | PK; unique chain; guard; envelope hash |
| Batch | `batch_id` (surrogate) + (`configuration_id`, `issuer_id`, `sequence`) + `partition_input_hash` | database; F6.4 | PK; unique chain; guard |
| Job | `job_id` (surrogate) | database | PK |

**Why surrogates.** Surrogate keys are used only where the database itself orders history (records, batches, jobs, designations), and compact child foreign keys need them. Their identity is always paired with content hashes. **No runtime timestamp is ever a key or part of one.**

### 11.2 Conflict behaviour

Every content-keyed INSERT uses `ON CONFLICT (<key>) DO NOTHING`. When nothing was inserted, the writer reads the stored row and requires every stored hash to equal the recomputed one:
- **equal:** the attempt is idempotent and is recorded as `already_present`;
- **different:** `NondeterminismError`. The transaction is rolled back, the job ends `failed` with `reason = nondeterminism` (§18.2), and nothing is written.

A natural-key collision with a different content key raises a unique violation, which is treated the same way. Two genuinely different validation runs always differ in their natural key, so they are two rows.

**The insert-if-absent registries (T4 facts, T8 configurations) are the exception.** A conflict there is the normal case, not a rerun:
- T4: a new validation run meets a fact another run already produced;
- T8: the same configuration is registered again.

The existing row is kept and checked against the recomputed one:
- T4: the identity columns (the database already tied them to `ef_key`, §8.3);
- T8: the envelope.

The job continues. Only the validation run's own key (T1) decides `already_present`.

### 11.3 Envelopes: exactly F6.3's hashed structures

| | Stored in | Exact text (F6.3 `canonical.canonical_json`) | SHA-256 equals |
|---|---|---|---|
| E1 | T1 `output_json` | `{"candidates": [[r.key, r.output_hash] …], "arithmetic": …, "signs": …, "statement_sign_conventions": …, "op1": …}` | `ValidationRun.output_hash` |
| E2 | T2 `output_json` | `{"validation": r.validation, "admission": r.admission}` | `CandidateResult.output_hash` |
| E3 | T5 `so_json` | `replace(so, output_hash="")` | `SourceObservation.output_hash` |
| E4 | T13 `result_json` | `replace(result, output_hash="")` | `ReconciliationResult.output_hash` |
| E5 | T8 `configuration_json` | `configuration` | `configuration_id` |
| E6 | T12 `output_json` | `{"configuration_id": …, "selection": …, "excluded_observations": …, "results": [[ef_key, output_hash] …]}` | `ReconciliationBatch.output_hash` |

The writer asserts each equality before inserting. The database re-checks it (`f6_envelope_hash_guard`). The input hashes (`ValidationRun.input_hash`, `CandidateResult.input_hash`) have no envelope, because inputs are referenced, not copied. They are verified by reproduction (§6.6).

Every envelope's typed columns and child rows are proven to be its exact decomposition (§11.6).

### 11.4 Partition fingerprint (`f6.store.1`)

`partition_input_hash = digest({"configuration_id": C, "issuer_id": I, "selection": <F6.3 Selection over the partition's runs>, "observations": [[so_key, so.output_hash] sorted by so_key]})`, computed with F6.3's `canonical.digest`.

F6.3's per-fact results are a pure function of exactly these inputs:
- the configuration;
- the selection, including the accepted runs and filings per document;
- the SOs, including the currency siblings in each document.

An equal fingerprint therefore implies equal results, and the pass is skipped.

### 11.5 Retry semantics

Every unit is idempotent. Re-running any job after any failure converges to the same rows:
- a validation, by its content and natural keys;
- a partition, by its fingerprint and the per-fact `input_hash` rule.

Retries are safe at any time, at any point of interruption (§18).

### 11.6 Envelope ↔ decomposition integrity

Each envelope (E1–E6) is the **only** authoritative representation of its F6.3 object. F6.4 also decomposes it into typed columns and child rows, so that it can be queried. That decomposition must never become a second, competing truth. So the database, and not only the writer, refuses to commit any decomposition that is not exactly what the envelope says:

```
F6.3 object ──canonical_json──▶ envelope + SHA-256                      authoritative
                                  │ the codec decomposes it (§17.5)
                                  ▼
typed columns + child rows ──database proves at INSERT and COMMIT──▶ decomposition == envelope
```

#### 11.6.1 The invariant

For every parent row P with envelope E, in every committed state of the database:

- **EDI-1 Reconstruction.** For every decomposed array A of E, the child rows of P, ordered by their ordinal, reconstruct A exactly: `E -> A = jsonb_agg(element(child) ORDER BY ordinal)`, with ordinals exactly 0 … length − 1.
  - This means the same membership, order, keys and source keys, and the same values: Decimals with their printed scale, half-units, tolerances and differences, nil state, reasons, sign-only flags, roles and reported representations.
  - No child is missing, extra or duplicated.
- **EDI-2 Typed columns.** Every typed column of P and of each child equals the field of E (or of the child's element) that it indexes, under the rules of §11.6.3.
- **EDI-3 Copies across levels.** Every value an element copies from another stored object equals that object (§11.6.4). For example, a member's F6.1 value equals its candidate validation's, and its reported value equals the F5 row. An observation reference equals its SO, and a pair's values equal its members'.
- **EDI-4 Keys.** Every content key whose inputs are all stored columns is recomputed by the database (§11.6.5).
- **EDI-5 Canonical order.** Every decomposed array is in the order frozen F6.3 emits. The database checks this from the child rows themselves (§11.6.6), so a reversed, duplicated or reordered pair can't commit, even if its envelope were written wrongly.
- **EDI-6 Seal.** No child row can be added to P in any transaction after P's own.

"Exactly" is jsonb equality between canonical JSON values. For F6.3 envelopes this is the same as byte equality of the canonical text, because:
- `canonical_json` is a deterministic, injective function of the structure;
- a nested value serialises identically standalone and in place;
- every JSON number is an integer (Decimals and dates are strings);
- jsonb strings compare exactly under the cluster's deterministic collation.

#### 11.6.2 What is decomposed, and how

| Envelope array | Child | Element held as | Ordinal | Order frozen F6.3 emits |
|---|---|---|---|---|
| E1 `candidates` | T2 | typed pair `[candidate_validation_key, output_hash]` | `candidate_ordinal` | F6.1 `validate_run`: by source key, (statement, row, column, value ordinal, concept) |
| E1 `op1` | T3 | copy `op1_json` | `op1_ordinal` | `op1.evaluate`: sorted (group key, concept) |
| E3 `members` | T6 | copy `member_json` | `member_ordinal` | `observations.member_order`: (statement, row, column, value ordinal, concept) |
| E3 `comparisons` | T7 | copy `comparison_json` | `comparison_ordinal` | `observations.observation`: member pairs (i, j), i < j, lexicographic; `a` = member i, `b` = member j |
| E4 `observations` | T14 | copy `observation_json` | `observation_ordinal` | `reconcile_fact`: (document_sha256, so_key) |
| E4 `comparisons` | T15 | copy `comparison_json` | `comparison_ordinal` | `reconcile_fact`: (i, j, p, q) lexicographic, where observations i < j, p is a member of i and q a member of j; `a` = (i, p), `b` = (j, q) |
| E6 `results` | T16 | typed pair `[ef_key, output_hash of its record]` | `result_ordinal` | `reconcile`: ef_key ascending |

Parents with typed columns: T1 ↔ E1, T2 ↔ E2, T5 ↔ E3, T8 ↔ E5, T12 ↔ E6, T13 ↔ E4 (and T3 ↔ its own element).

**Not decomposed.** These parts live only in the envelope, which is authoritative for them, and reproduction verifies them (§6.6):
- E1 `arithmetic`, `signs` and `statement_sign_conventions`;
- E2's F6.1 sub-results beyond the typed columns;
- E3 `f5_run` / `document` beyond the fields checked below;
- E4 `context`;
- E6 `selection` and `excluded_observations`.

**Why five arrays are held as element copies.** Their elements can't be rebuilt from a queryable subset of columns:
- an SO member has 31 fields, including F6.1's `ValueResult` and the verbatim reported value;
- an observation reference has 16 fields;
- the comparisons carry F6.1's `ComparisonResult`;
- an OP1 record carries its terms.

A per-child copy makes the reconstruction literal and complete, and one structural comparison proves it. The copy is **not** a source of truth:
- the codec writes it from the same F6.3 object;
- it is proven equal to the parent's element before commit and can never change afterwards;
- every reader who needs the whole object reads the parent envelope.

The two pair arrays are fully typed and need no copy.

#### 11.6.3 Exact comparison rules

**The comparison.** A typed value `v` is compared with a JSON field by `f6_field_eq(e, path, v)` ≡ `e #> path IS NOT NULL AND e #> path = coalesce(v, 'null'::jsonb)`. A missing field fails. SQL NULL matches only JSON null.

**Converting a typed value to canonical JSON:**

| Typed value | Its canonical JSON `v` |
|---|---|
| text, integer types, boolean, text[] of codes (reasons, annotations, roles, T2 `nil_form`) | `to_jsonb(col)` |
| numeric | `f6_num_json(col)` = `to_jsonb(col::text)`. This is plain notation with the stored display scale, equal to F6.3's `format(d, 'f')` on the production path (§13.2). `1.0` ≠ `1.00` |
| date | `f6_date_json(col)` = `to_jsonb(to_char(col, 'YYYY-MM-DD'))` |
| uuid | `to_jsonb(col::text)` (lower-case canonical) |
| T5 `nil_forms` (C4 `a:b` strings) | `f6_nil_forms_json(col)`: the array of `:`-split arrays |
| a source key (T2 plus its run) | `f6_source_key_json(f5_run_id, si, ri, ci, vo, concept_key)` = `[f5_run_id::text, si, ri, ci, vo, coalesce(concept_key, '')]` |
| a whole sub-object (element copies, `value`, `reported`, `identity`) | `col::jsonb`, or the F5 / T4 row rendered field by field with these rules |

**Typed column ↔ JSON path:**
- **T1 ↔ E1:** `candidates_total` = length(`candidates`); `op1_count` = length(`op1`).
- **T2 ↔ E2:**
  - `statement_index`, `row_index`, `column_index`, `value_ordinal` = `validation.source_key[1..4]`, and T1's `f5_run_id` = `source_key[0]`;
  - `concept_key`, `candidate_id`, `eligibility`, `ineligible_reasons`, `normalization_reasons` = `validation.*`;
  - `admitted`, `value_kind`, `nil_form`, `lifted_reasons`, `operations_route`, `ef_key` = `admission.*`; `admission_reasons` = `admission.reasons`; `op1_key` = `admission.op1_record`.
- **T3 ↔ its element:**
  - `op1_key` = `key`; `op1_version` = `version`;
  - `statement_root` … `role` = `group_key[0..6]`, where `""` and `-1` ↔ NULL;
  - `concept_key`, `outcome`, `reasons`, `currency`, `value_type`, `computed`, `total`, `tolerance`, `difference` = the same names;
  - `validated_candidate_ids` = `validated`, mapped through T2's source keys in order (checked at commit).
- **T5 ↔ E3:**
  - `so_key`, `ef_key`, `validation_run_key` = the same names;
  - `f5_run_id`, `cse_filing_id`, `document_sha256` = `f5_run.*`;
  - `observation_status`, `value_kind`, `nil_forms`, `normalized_value`, `half_unit`, `precision`, `interval_low`, `interval_high`, `roles`, `annotations` = the same names;
  - `member_count` = length(`members`);
  - `reported_*` = `reported.{raw_value, parsed_value, representation_class, printed_decimals, sign_as_printed, reported_scale, scale_basis, currency, value_type}`;
  - `representative_candidate_validation_key` = the member whose `source_key` = `representative_member` (checked at commit);
  - `identity` = the T4 row; `versions` = T1's five versions; `output_hash` = `""`.
- **T6 ↔ `member_json`:**
  - `candidate_validation_key`, `candidate_id`, `value_kind`, `role`, `period_derivation`, `operations_route`, `maturity_basis`, `audit_label_reported`, `restated` = the same names;
  - `normalized_value`, `half_unit`, `currency`, `value_type` = `value.*`.
- **T7 ↔ `comparison_json`:**
  - `outcome`, `reason`, `sign_only` = the same names;
  - `a_value` … `abs_difference` = `comparison.*` (all NULL ↔ `comparison` null);
  - `a` / `b` = the source keys of the members at `a_member_ordinal` / `b_member_ordinal`.
- **T8 ↔ E5:** `reconciliation_version` = the same name; the five versions = `versions.*`.
- **T12 ↔ E6:** `configuration_id` = the same name; `results_count` = length(`results`).
- **T13 ↔ E4:**
  - `ef_key`, `configuration_id`, `reconciliation_version`, `input_hash`, `state`, `value_kind`, `interval_low`, `interval_high`, `representative_normalized_value`, `representative_half_unit`, `document_count`, `annotations`, `reasons` = the same names;
  - `so_count` = length(`observations`); `comparison_count` = length(`comparisons`);
  - `representative_so_key` = `representative_so`;
  - `representative_candidate_validation_key` = the member of that SO whose `source_key` = `representative_member`;
  - `reported_*` = `representative.*`;
  - `identity` = the T4 row; `output_hash` = `""`.
- **T14 ↔ `observation_json`:** `so_key`, `so_output_hash`, `document_sha256`, `role_in_outcome` = the same names.
- **T15 ↔ `comparison_json`:**
  - `a_so_key` = `a_so`; `b_so_key` = `b_so`;
  - `a_member` / `b_member` = the source keys of the members at (`a_so_key`, `a_member_ordinal`) / (`b_so_key`, `b_member_ordinal`);
  - `outcome`, `reason`, `sign_only` = the same names; `a_value` … `abs_difference` = `comparison.*`.
- **T16 ↔ E6 `results[result_ordinal]`:** `[ef_key, output_hash of T13(record_id)]`. For a fact the pass did not append, this equality with the existing record's `output_hash` is also a nondeterminism check.

#### 11.6.4 Copies across levels (EDI-3)

| Element | Must equal |
|---|---|
| T6 `member_json` | `source_key`, `candidate_id`, `candidate_validation_key`, `statement_index`, `row_index`, `column_index`, `value_ordinal` = its T2 row; `value` = E2 `validation.value`; `value_kind`, `nil_form`, `operations_route`, `op1_record` = E2 `admission.*`; `reported` = the F5 candidate row (`raw_value`, `parsed_value`, `representation_class`, `printed_decimals`, `sign_as_printed`, `reported_scale`, `scale_basis`, `reported_currency` → `currency`, `value_type`) |
| E3 (T5) | `reported`, `normalized_value`, `half_unit` = the representative member's `reported`, `value.normalized_value`, `value.half_unit` (null without a representative; value fields null for nil) |
| T7 / T15 `comparison_json` whose `comparison` is not null | `a_value`, `a_half_unit`, `currency`, `value_type` = member a's `value.*`; `b_value`, `b_half_unit` = member b's |
| T14 `observation_json` | `so_output_hash` = T5 `output_hash`; `document_sha256`, `cse_filing_id`, `f5_run_id` = E3 `f5_run.*`; `observation_status`, `value_kind`, `reported`, `normalized_value`, `half_unit`, `interval_low`, `interval_high`, `roles` = E3's; `document_type`, `underlying_type` = E3 `document.*` |
| E4 (T13) | `representative`, `representative_normalized_value`, `representative_half_unit` = the representative member's `reported`, `value.normalized_value`, `value.half_unit` |

#### 11.6.5 Keys recomputed by the database (EDI-4)

Each key is `encode(sha256(convert_to(t, 'UTF8')), 'hex')` of this ASCII text `t`:

| Key | `t` |
|---|---|
| `validation_run_key` (T1) | `["validation_run",{"admission_version":"<a>","identity_version":"<i>","input_policy_version":"<p>","op1_version":"<o>","validation_version":"<v>"},"<f5_run_id>","<input_hash>"]` |
| `candidate_validation_key` (T2) | `["candidate_validation","<validation_run_key>",["<f5_run_id>",<statement_index>,<row_index>,<column_index>,<value_ordinal>,"<concept_key or empty>"]]` |
| `op1_key` (T3) | `["op1","<op1_version>",[<statement_root>,"<statement_kind>","<period_kind or empty>","<period_end YYYY-MM-DD or empty>",<duration_months or -1>,"<reported_scope or empty>","<role or empty>"],"<concept_key>"]` |
| `so_key` (T5) | `["source_observation","<validation_run_key>","<ef_key>"]` |
| `ef_key` (T4) | §8.3 |
| `output_hash`, `configuration_id` | SHA-256 of the envelope (§5.2 C2) |

**Why the text is byte-exact.** It equals F6.3's `canonical_json` because every part is restricted, by CHECKs and foreign keys, to characters JSON never escapes:
- lower-case hex keys and canonical uuids;
- the version patterns;
- `[a-z0-9_]` concepts (0008);
- enumerated kinds, scopes and roles (`chk_fop1_group`);
- ISO dates and integers.

**Not recomputed.** The record's `input_hash`, and the validation and candidate `input_hash`es, have preimages that are not stored. Reproduction verifies them (§6.6).

#### 11.6.6 Canonical order (EDI-5)

These are checked in the parent's commit-time trigger, from the child rows' typed columns. Text is compared `COLLATE "C"` (Python's code-point order) and integers numerically.

| Child | Required |
|---|---|
| T2 | by `candidate_ordinal`: (`statement_index`, `row_index`, `column_index`, `value_ordinal`, `coalesce(concept_key, '')`) strictly increasing |
| T3 | by `op1_ordinal`: (`statement_root`, `statement_kind`, `coalesce(period_kind, '')`, `coalesce(to_char(period_end, 'YYYY-MM-DD'), '')`, `coalesce(duration_months, -1)`, `coalesce(reported_scope, '')`, `coalesce(role, '')`, `concept_key`) strictly increasing |
| T6 | by `member_ordinal`: the member's T2 (`statement_index`, `row_index`, `column_index`, `value_ordinal`, `coalesce(concept_key, '')`) strictly increasing |
| T7 | the sequence of (`a_member_ordinal`, `b_member_ordinal`) by `comparison_ordinal` = exactly the pairs (i, j) with 0 ≤ i < j < `member_count`, lexicographic |
| T14 | by `observation_ordinal`: (`document_sha256`, `so_key`) strictly increasing |
| T15 | the sequence of (`a_observation_ordinal`, `b_observation_ordinal`, `a_member_ordinal`, `b_member_ordinal`) by `comparison_ordinal` = exactly the tuples (i, j, p, q) with i < j < `so_count`, p < `member_count` of observation i and q < `member_count` of observation j, lexicographic |
| T16 | by `result_ordinal`: `ef_key` strictly increasing |

**How the pair checks work.** The T7 and T15 checks compare the stored sequence with one generated in SQL (`generate_series`). A missing, extra, duplicated, reversed or reordered pair therefore fails.

**What ties the ordinals to the rows.**
- Composite foreign keys tie (`so_key`, `candidate_validation_key`, `member_ordinal`) to T6, and (`record_id`, `so_key`, `observation_ordinal`) to T14.
- CHECKs require `a_member_ordinal < b_member_ordinal` (T7) and `a_observation_ordinal < b_observation_ordinal` (T15).

So a reversed pair fails three independent ways: the CHECK, the sequence, and EDI-1.

#### 11.6.7 Where the database enforces it

| Part | Mechanism | Runs at |
|---|---|---|
| EDI-2, EDI-3 and EDI-4, where the referenced rows exist at insert time | the row's BEFORE INSERT guard (§5.4). The writer inserts referenced rows first (§6.1, §9.4), and composite foreign keys guarantee they exist | INSERT |
| EDI-1, EDI-5, and the fields that need children (T3 `validated_candidate_ids`; the T5 and T13 representative member; E3's representative copies) | the parent's deferred completeness trigger (§5.5). It parses the envelope once and checks every child in one set-based query | COMMIT of the parent's transaction |
| EDI-6 | `f6_child_seal()` on every child table (§5.5): the parent's child count must equal its verified count | COMMIT of **every** transaction that inserts a child |

**The EDI-1 check, exactly.** For each decomposed array A of E:

```
E -> A = coalesce(jsonb_agg(element ORDER BY ordinal), '[]'::jsonb)
coalesce(max(ordinal), -1) = jsonb_array_length(E -> A) - 1
```

With the per-parent unique ordinal and `ordinal >= 0`, these two equalities make the ordinals exactly 0 … length − 1. Every child is then the element at its own position.

**Why the seal is sufficient.**
- A parent's count is proven equal to its envelope's array length when the parent commits.
- Rows are never deleted: `f5_reject_mutation()` stops every role, and no role has DELETE.
- So any later child pushes the count past the verified count, and that transaction can't commit.
- The seal sits on the child tables because a parent's deferred trigger fires only in the parent's own transaction.

**Guard rails against a weaker implementation.**
- **One helper per rule.** The comparison rules exist once, as the pure helper functions of §11.6.3. Every guard uses them, and tests U10 and P18 cover every listed field of every table.
- **One order per array.** Each order check implements exactly the order in §11.6.6. A later F6.3 version that changes an order, a field or an encoding needs a new migration stating the new rule, never an edit to 0015.
- **Python checks first.** The writer builds the children from the same F6.3 object and asserts the whole invariant in Python before INSERT, for early, readable errors. The database checks stay the authority.

#### 11.6.8 What the database deliberately does not do

- **It does not recompute F6.1 or F6.3 semantics.** Tolerances and differences (F6.1's `abs()` depends on the pinned Decimal context, §17.4), intervals, representatives, states and OP1 outcomes are not recomputed. Doing so in SQL would be a second implementation of F6.3 (B2).
- **What the database proves:** the stored decomposition is exactly the stored envelope; copies agree across levels; nothing can be added or changed afterwards.
- **What reproduction proves:** that the envelope is F6.3's correct output for its referenced inputs (`verify`, §6.6, §17.6).
- **Who can still bypass it:** the owner through DDL (`DISABLE TRIGGER`), or a superuser, as with every append-only rule (§14 M2). No service role can.

#### 11.6.9 Evidence and cost

- **Corpus probe.** A scratch probe (not in the repository) ran the 26-filing corpus through frozen F6.3 and found 0 exceptions:
  - every element's canonical text equals its text inside the parent envelope;
  - every JSON number in E1–E6 is an integer, and every Decimal string is fixed-point;
  - all seven orders hold, over 1,826 members, 96 member pairs, 1,746 observation references and 286 cross-SO pairs;
  - every copy relation of §11.6.4 holds;
  - the §11.6.5 templates reproduce all 26 validation-run, 2,248 candidate-validation, 12 OP1 and 1,746 SO and fact keys.
- **PostgreSQL behaviour.** The probe could not test what the mechanism relies on inside PostgreSQL 17: jsonb equality, `numeric::text` and `sha256()`. Tests P18 prove these on PostgreSQL 17 (§21).
- **Cost.** Each envelope is parsed once at commit (corpus means: E1 57 KB, E3 4.3 KB, E4 2.6 KB). The element copies add about 1.4 GB per full generation (§20).

## 12. Timestamp/as-of boundary

### 12.1 Economic identity dates (part of the identity)

`period_end` and `duration_months` (null for instants). They come only from F3/F5 period evidence, validated by F6.1. They are never derived: no Q4 = FY − 9M, no quarter from YTD, nothing from titles, `manualDate` or an inferred FYE (F6.2 §8.4).

`period_start` is **not** identity. It is the member's printed start (E3) and F5's `financial_statement_columns.start_date`.

### 12.2 Source and document dates (evidence, never policy)

- F1: `report_filings.uploaded_at` / `authorized_at` with their raw strings, and `report_filing_observations.observed_at`.
- The F5 run's raw snapshot: uploaded, authorized, path epoch, CDN Last-Modified, F1 first-seen, retrieval time.
- T1 `publication_uploaded_at` / `publication_date`. This is the input to F6.1's `period_end_after_publication` **sanity check only** (D-7). **It is not an availability time.**

### 12.3 Runtime timestamps (system knowledge; never inputs to F6.3, never in keys, hashes or identity)

- `recorded_at` (T1, T5, T8, T9, T12, T13), `first_recorded_at` (T4):
  - `now()` of the inserting transaction, which in PostgreSQL is the time the **transaction started**;
  - the row became visible at its COMMIT, which is later.
  - It means "this database held the row from its commit, and the writing transaction began at `recorded_at`".
  - It does **not** mean publication, availability, first-seen, retrieval or processing-start time of any source.
- `started_at` / `finished_at` (T1): the wall-clock duration of the F6.3 computation. Provenance only.
- Job times (T10 `started_at`, T11 `occurred_at`): operational.
- The F5 run's own `recorded_at` **is** an F6.3 input: it drives D-6 selection and is hashed inside `F5RunRef`. It is F5's immutable system-knowledge time and never F6.4's runtime.

**Why this cannot leak into identity or values.** F6.3 is pure. The loader passes no F6.4 runtime value into it. Keys, hashes and identities are computed before the INSERT, and `recorded_at` defaults are set by the database afterwards.

### 12.4 Future as-of semantics (F8; NOT implemented)

F6.4 implements no availability, supersession or as-of policy, and no "knowledge cutoff" parameter. It preserves what F6.2 §9.2 needs:
- **Q1 ("what did the system conclude at T")**: records with `recorded_at` ≤ T.
  - *Caveat, for F8:* transaction-start time is not commit time.
  - An exact commit-time as-of needs `track_commit_timestamp = on`, which is a P1 server-configuration decision (§23 Q6).
- **Q2 ("what could it have concluded at T")**: F5 `recorded_at`, `filing_issuer_links.decided_at`, `classified_at`, `report_filing_observations`, T1 input references, then a recomputation.
- **Q3 (retrospective source availability)**: the raw availability evidence above, under an F8 policy.

No F6.4 view is labelled or behaves as an as-of view.

## 13. Decimal/currency/nil storage

### 13.1 Unconstrained `numeric`

Every Decimal column is `numeric` **without precision or scale**:
- `normalized_value`, `half_unit`, `precision`;
- interval bounds, `tolerance`, `abs_difference`, `a_value` / `b_value`;
- OP1 `computed` / `total` / `difference`;
- the reported `parsed_value` copies.

**Why not `numeric(p, s)`:**
- PostgreSQL **rounds** input to the declared scale, silently, which would alter printed values such as 1.2345 per-share amounts or sub-unit half-units;
- it rejects values beyond the precision;
- F6.3 computes exactly, in an 80-digit context that raises on inexact results, and F6.1 normalises exactly (`parsed × scale`), so no fixed scale is safe.

**What unconstrained `numeric` gives:** it stores the exact value **and its display scale**. `1234000.0` stays `1234000.0`, and psycopg2 returns `Decimal('1234000.0')`. It supports up to 131,072 digits before the point and 16,383 after, far beyond any F6 value.

**Other number types:** no binary float anywhere; `bigint` for reported scales; `smallint` for indices and printed decimals; `integer` for counts.

### 13.2 Exactness and round trip

- **Writing.** The writer passes Python `Decimal` objects straight to psycopg2, which adapts them as exact numeric literals. Values never pass through `str` + `float`, or through JSON numbers.
- **Round trip.** For every value F6.3 emits on the production path, `format(Decimal_read_back, 'f') == format(Decimal_written, 'f')`. This keeps the typed columns and the envelopes consistent, and the guards compare the typed column's text with the envelope's string.
- **Non-finite values** are refused by CHECKs (`'NaN'`, `'Infinity'`, `'-Infinity'`). F6.3 never produces them.
- **Negative zero.**
  - PostgreSQL `numeric` has no negative zero. F5 already stores `parsed_value` as `numeric`, so a printed `-0` is stored as 0, with its printed sign kept in `representation_class = 'negative_zero'` and `sign_as_printed`.
  - Because F6.4 validates only from persisted F5 rows (B3), F6.3 never sees `Decimal('-0')` on the production path, and every stored value round-trips.
  - The envelope stays the authoritative byte-exact record in any case.

### 13.3 Currency

- **Identity column:** `financial_economic_facts.currency`, with `^[A-Z]{3}$` and **no default**. F6.1 already refuses a missing or unrecognised currency (`currency_not_reported` / `currency_unrecognised`), so such a candidate is never admitted.
- **Everywhere else:** reported currencies are copied verbatim.
- **No FX:** there is no conversion column, rate table or implicit LKR anywhere. Facts of different currencies are different facts.
- **Annotations:** `multi_currency_presentation` records a presentation in two currencies without ranking them.

### 13.4 Nil

- **Where nil is stated:** `value_kind = 'nil'` (T2, T5, T6, T13) is the only statement of nil. The numeric columns are then NULL, which the CHECKs tie together.
- **Nil forms:** kept as `nil_form` / `nil_forms`.
- **Zero:** a printed `0` is `value_kind = 'numeric'` with `normalized_value = 0`, a different row state.
- **NULL is never nil by itself.** A consumer that reads NULL without `value_kind` cannot mistake it for zero or for nil: the kind column is NOT NULL wherever a value exists.
- **Missing values** (blank, N/A, text) are not observations at all. They exist only as non-admitted T2 rows with their F6.1 reasons (F6.2 §8.1).

### 13.5 Reported representation

These are verbatim copies of the F5 row, the source of truth, and the guards check that the copies equal it:
- `raw_value`
- `parsed_value`
- `representation_class`
- `printed_decimals`
- `sign_as_printed`
- `reported_scale`
- `scale_basis`
- `reported_currency`
- `value_type`

The normalised value is stored **beside** the reported one, never in its place (F6.2 §4 "reported evidence is never mutated"). No sign is flipped: `sign_only_difference` is an annotation computed by F6.3 on a negated **copy**.

## 14. Append-only/mutability model

| Table | Class | UPDATE | DELETE / TRUNCATE | Notes |
|---|---|---|---|---|
| T1–T3, T5–T8, T10, T12, T14–T16 | immutable after insert | never (trigger) | never (trigger) | Content-keyed or surrogate; complete at commit (§5.5) |
| T4 | immutable, insert-if-absent | never | never | Identity registry; no values |
| T9, T11, T13 | append-only chains | never | never | The latest row by `id`, `seq` or `sequence` is "current"; a guard enforces order |
| V1–V6 | projections | n/a | n/a | Views: rebuildable, never written, never authoritative |

- **M1. There is no mutable table in F6.4** and no UPDATE path at all, operational metadata included. States are events (T11), history is chains (T13, T12, T9), and "current" is a view.
- **M2. Protection.**
  - `f5_reject_mutation()` rejects UPDATE, DELETE and TRUNCATE for **every** role, the owner included (0007 and 0010 semantics, errcode `23001`).
  - The worker additionally lacks those privileges.
  - Only the owner explicitly running `ALTER TABLE … DISABLE TRIGGER` inside a deliberate procedure, or a superuser, can bypass this. No service is either.
- **M3. A newer validation never deletes an older one** (M1 of §6.5), and a newer reconciliation record never replaces an older one: it appends.
- **M3a. Decompositions are sealed.** A parent's children are exactly those committed with it (§11.6):
  - nothing can be updated or deleted (M2);
  - the seal triggers refuse any child added later.

  Append-only therefore also means "complete at commit, closed afterwards".
- **M4. Purge.** F6 rows are "F-stage data derived from CSE documents". Whether they fall in the scope of a G-1 purge is an owner decision already listed in P2 §12. F6.4 ships **no** purge code, function or grant. If they are in scope, the future FULL-gated purge phase handles them with P2 §12's pattern:
  - one owner transaction;
  - triggers disabled for its duration only;
  - deletion in foreign-key order, children first: T15, T16, T14, T13, T12, T7, T6, T5, T2, T3, T4, T1, T11, T10. T4 comes before T1 because `first_validation_run_key` references T1, and T10 comes last because T1, T11 and T12 reference it. T8 and T9 are kept, since they contain no CSE content;
  - an audit row.

## 15. PostgreSQL security model

### 15.1 Ownership

The runner creates every 0015 object as `cse_owner` (`SET LOCAL ROLE`). No LOGIN role owns anything. No SECURITY DEFINER function exists. All functions are plpgsql and SECURITY INVOKER.

### 15.2 Privileges

| Object | `cse_worker` | `cse_reader` | `cse_backup` | `cse_owner` |
|---|---|---|---|---|
| T1–T8, T10–T16 | SELECT, INSERT | SELECT | read via `pg_read_all_data` | owner |
| T9 designations | SELECT | SELECT | read | INSERT via the owner path only |
| V1–V6 | SELECT | SELECT | read | owner |
| 0015 trigger functions | none (EXECUTE revoked from PUBLIC; PostgreSQL checks no EXECUTE privilege when a trigger fires, the 0013/0014 precedent) | none | none | owner |
| 0015 pure helper functions (§11.6.3) | EXECUTE (the worker's guards call them in its own session) | none | none | owner |
| Existing inputs (0004, 0005, 0007, 0008) | unchanged (0009 already grants SELECT) | unchanged | unchanged | unchanged |
| PUBLIC | nothing | | | |

- **No grant of UPDATE, DELETE or TRUNCATE on any 0015 object to any role.** P1's `verify_server` rule `no_delete_or_truncate_grants` covers every relation generically.
- **No sequence grants.** Identity columns (T9, T13) need no separate sequence privilege for an INSERT-privileged role; `market_schedule_wakeups` in 0014 is the precedent.
- **Reader.** 0009's default privileges already grant `cse_reader` SELECT on new owner-created tables. 0015 grants explicitly anyway, as 0012 and 0014 do.

### 15.3 Row-level security

**Not used.**
- The system is a single-tenant local cluster, with a socket-only, peer-authenticated boundary (0009 replaced the Supabase-era RLS plan).
- Every service role sees whole tables.
- Isolation is by role privileges and triggers.

### 15.4 Worker writes are direct, not owner-mediated

All F6 outputs are append-only derived evidence produced by the worker job, exactly as F5's rows are. Protection comes from INSERT-only privileges, append-only triggers and the guards.

**The only owner-mediated write is T9**, a policy decision, via `cse_migrator` → `SET LOCAL ROLE cse_owner`, as P2's `acknowledge-block` and P3's `arm` are.

### 15.5 Guard function authority

Guards read only tables the inserting role can SELECT: F5, F3, F1, the 0007 tables and F6. None needs elevated rights.

### 15.6 F6.4 preflight

This is `worker/financial_truth_store/preflight.py`, run before every job that writes. It is modelled on P3's `preflight.py` and reuses P2's `runs.security_preflight` role checks:
- the session is `cse_worker`: not a superuser, not the owner, not a member of `cse_owner`, `cse_migrator`, `cse_backup` or `pg_read_all_data`;
- **exactly** SELECT + INSERT on T1–T8 and T10–T16, SELECT only on T9 and V1–V6, and EXECUTE on the §11.6.3 helper functions;
- no UPDATE, DELETE or TRUNCATE anywhere in F6;
- every 0015 trigger exists and is enabled, including every `f6_child_seal()` trigger (§11.6.7).

Any problem refuses the job (exit 5) before anything is written.

Adding F6 tables to P1's frozen `verify_server.APPEND_ONLY` list would be a P1 change, and is not proposed (§23 Q4).

### 15.7 Locks

`F6_LOCK_KEY = 4_346_836_117_002_313`.
- The migration runner uses `…311` and P2's capture lock `…312`, which P3 shares. The implementation checks, by grep, that `…313` is unused.
- **Reconcile and cleanup** jobs take it **exclusively** (`pg_try_advisory_lock`). If it is busy, the job ends `refused` / `busy` with exit 0.
- **Validate** jobs take it **shared**. They may run concurrently with each other (content keys resolve races), never with a reconcile pass.
- F6 jobs never take the P2 capture lock. They contact no one, and CSE capture is unaffected.

### 16.7 Rollback philosophy

- **Forward-only.** There are no down-migrations (P1 runner).
- **Additive.** 0015 adds objects and alters nothing, so applying it cannot damage existing data.
- **A failed apply** rolls back completely (one transaction; P1 test `test_failed_migration_rolls_back_completely`).
- **Before applying,** take a local dump (P1 §5, §10).
- **A defect found after apply** is fixed by a new migration, never by editing 0015.
- **Data-level rollback** means restoring the pre-migration dump, only for a severe incident, and it discards later data.

### 17.3 Loader contract (rendering rules of `f6.store.1`)

- **L1.** The F5 result dict is rebuilt from the 0008 rows in exactly the JSON-form shape `financial_validation.contexts_from_f5_result` and F6.3 `candidate_attributes` read:
  - `run`: the F5 run key fields and `timestamps`;
  - `statements`, with `statement_index`, `statement_kind` and `continuation_of`;
  - `columns`: every 0008 column field;
  - `rows`, with `operations` and `operations_basis`;
  - `candidates`: every 0008 field plus `id`, with `statement_index`, `row_index` and `column_index` resolved through the extract, row and column foreign keys.
- **L2. Timestamps.** Every `timestamptz` is rendered as `value.astimezone(timezone.utc).isoformat()`, identical to F5's `timestamp_snapshot` (`_ts`). Dates are `date` objects. The session runs with P1's fixed settings (`dbhash.SESSION_SETTINGS`: `timezone UTC`, ISO datestyle).
- **L3. Scalars.** `numeric` is read as `Decimal`, never float; `smallint`/`integer`/`bigint` as `int`; arrays as lists.
- **L4. Identifiers.** A uuid is rendered as its canonical lower-case text: the `F5RunRef.f5_run_id`, `classification_id`, the issuer `issuer_id`, and the source key's run part.
- **L5. `F5RunRef`** carries `recorded_at`, `classification_id` and `content_sha256` from the run row, **always**.
- **L6. `IssuerLinkDecision`** comes from the `filing_issuer_links` row: `id`, `cse_filing_id`, `status`, `basis`, `issuer_id`, `decided_at`. **`DocumentContext`** comes from the classification row, including its `id`. **The publication input** is `report_filings.uploaded_at`, with the value taken from T1 on reproduction.
- **L7. Candidate ids** are always present (`id`). A candidate without an id cannot be persisted.

### 17.4 Decimal context (closes the F6.3 audit's inherited F6.1 caveat)

Every F6.4 call into F6.3 runs inside `decimal.localcontext(F6_DECIMAL_CONTEXT)`, a freshly constructed context equal to Python's documented default:
- `prec = 28`;
- `rounding = ROUND_HALF_EVEN`;
- `Emin = -999999`, `Emax = 999999`;
- `capitals = 1`, `clamp = 0`;
- traps `InvalidOperation`, `DivisionByZero`, `Overflow`.

F6.1's `compare_values`, which uses the ambient context for `abs()`, therefore behaves exactly as validated, whatever context the calling process has set. F6.3's own arithmetic is independent of the context anyway.

### 17.5 Codec (serialization boundary)

- **Out.** F6.3 dataclasses → typed column values (plain attribute reads) + envelopes E1–E6 via F6.3's `canonical_json`. No other JSON format exists.
- **In.** E3, E4 and E5 → F6.3 dataclasses via an explicit type registry, for example:
  - `SourceObservation.members` → `tuple[SOMember]`;
  - `SOMember.value` → `ValueResult`;
  - `MemberComparison.comparison` → `ComparisonResult`.

  Decimal fields are rebuilt as `Decimal(<string>)`, dates from ISO strings, and lists become tuples.
- **The round-trip invariant** is checked on every decode: `canonical_json(decode(envelope)) == envelope`. The decoded object therefore hashes to the stored `output_hash`. The reconcile job reconciles **decoded, stored SOs**, never silently recomputed ones.
- **Decomposition.** The codec derives every child row from the same F6.3 object as its envelope:
  - the ordinal is the element's position in F6.3's array;
  - the element copy is `canonical_json(element)`;
  - the typed columns follow the rules of §11.6.3.

  Before any INSERT, it asserts in Python the invariant the database enforces (§11.6): reconstruction, typed exactness, copies, keys and order. It refuses any JSON number that is not an integer.

| 4 | PostgreSQL unavailable |
| 5 | Refused or failed (§18.2): preflight, input error, transaction failure, nondeterminism, `inputs_changed`, version or configuration mismatch, `--no-validate` with missing runs |

## 18. Failure/retry semantics

### 18.1 Atomic units

| Unit | One transaction contains | Isolation |
|---|---|---|
| Validation of one F5 run | T1 + T3 + T4 (insert-if-absent) + T2 + T5 + T6 + T7 + the final `succeeded` T11 event | READ COMMITTED (all inputs immutable except `report_filings`, which is read once) |
| Partition pass | T12 + T13 + T14 + T15 + T16 | REPEATABLE READ (one consistent snapshot of runs, validation runs, SOs, latest records and latest batch) |
| Job start; a reconcile job's final event; any refusal or failure | T10 + T11 `started`; later T11 `succeeded` (reconcile, after its last partition) / `failed` / `refused` / `abandoned` | autocommit (outside the data transactions) |

The deferred completeness triggers (§5.5) make a partial parent **uncommittable**.

### 18.2 Cases

| Case | Behaviour | Guarantee |
|---|---|---|
| Database unavailable | Exit 4 before any write; no job row may exist; retry later | Nothing half-written |
| Transaction failure (constraint, guard, deferred check, serialization) | Full rollback; T11 `failed` with error class and redacted message (autocommit); exit 5 | No partial rows |
| Duplicate persistence attempt | `ON CONFLICT DO NOTHING`; stored hashes compared; equal → rollback + T11 `already_present`, exit 0 | No duplicate truth |
| Same content key with different hashes, or same natural key with a different content key | `NondeterminismError`; rollback; T11 `failed` (`reason = nondeterminism`); exit 5; operator investigates | Never overwrite, never fork silently |
| Partial batch failure (one partition fails) | That partition rolls back; earlier partitions stay committed and complete; the job ends `failed` with the partitions done or failed; rerun resumes (fingerprints skip completed ones) | No half-written reconciliation state |
| Validation succeeds, persistence fails | Nothing persisted; rerun recomputes (pure) | No silently missing observations |
| Persistence commits, then the process crashes before acknowledging | The `succeeded` event committed **with** the data; the next run finds the content key → `already_present` | Never a false success, never a lost one |
| Crash mid-reconcile | Committed partitions complete; the job lacks a final event → `cleanup` (or the next reconcile, holding the lock) marks it `abandoned`; rerun continues | Resumable |
| Two reconcile jobs | The second cannot take the exclusive lock → `refused`/`busy`, exit 0 | Single appender per chain |
| Validate while reconcile runs | Waits for the shared lock (or is refused with `--nowait`) | Consistent snapshots |
| Missing canonical validation run during reconcile | Validated first (a child `validate` job); with `--no-validate` → `refused`, exit 5 | Never falls back to other inputs |
| Inputs change during a reconcile pass (a new F5 run, issuer decision or `uploaded_at` committed after step 2) | The affected partition finds a selected run without its canonical validation run in its snapshot and is rolled back unwritten (`inputs_changed`); other partitions proceed; the job ends `failed`, exit 5; a rerun validates and completes it | A document is never reconciled without its current observations |
| F6.3 raises `InputError` for an F5 run | Job `failed` for that run; no rows; reported | Fail-closed |
| A decomposition differs from its envelope: a wrong or re-scaled value, a missing, extra, duplicated, reversed or reordered child, a wrong copy or a wrong key | Refused by the child's guard at INSERT, or by the parent's completeness trigger at COMMIT; full rollback; T11 `failed` (`reason = decomposition_mismatch`); exit 5. The writer's own pre-insert assertion normally stops it first | No envelope ever commits with a decomposition that is not exactly its own (§11.6) |
| A child row inserted for an already committed parent | Refused at COMMIT by `f6_child_seal()` | Committed decompositions are never extended |

"Success" is reported only after `COMMIT` returns. There is no retry storm: a job either succeeds, is already present, or ends with a recorded final state.

## 19. Backup/restore implications

- **Dumps include F6.4 automatically.** P1's `pg_dump -Fc` dumps the whole database from an exported snapshot, so every 0015 table, view, function and trigger is in each dump with its owner and ACLs. `globals.sql` carries the roles.
- **The restore check covers F6.4 automatically.** P1's `restore_check` and `dbhash` digest **every table** in `public`/`ops` (order-independent row digests under fixed session settings), plus the trigger list and the migration ledger.
- **On the restored copy, run `verify`.** `pg_restore` creates triggers after loading data, so the insert guards do not re-run during a restore. F6.4's `verify` provides that re-check: envelope hashes, codec round trips, the §11.6 decomposition invariant, chains, completeness, and a sampled reproduction from F5 rows. Its result is not a P1 ledger item.
- **Explainability without PDFs.** The whole chain, from the F5 cells to the reconciliation, is in the database (§10). A restored database answers "why this fact has this state" (§9.8) with no document.
- **G-1.** Dumps contain F-stage data derived from CSE documents. They stay private, encrypted off-site, and never in Git. Purge scope: §14 M4.
- **No change** to the P1 backup units, schedules, ledger or off-site design.

## 20. Performance considerations

**Volume** (per full generation of a 5-year backfill; about 7,900 filings):
- Row counts per filing come from F6.2 §12 and the corpus.
- Envelope and element sizes are corpus means measured for revision 2. Revision 1 had estimated E2 at 1.2 KB, E3 at 3 KB and E4 at 2.5 KB.

| Table | Rows | Approximate bytes/row (typed + envelope or element copy) | Approximate total |
|---|---|---|---|
| T2 candidate validations | ~683 k (86.5/filing) | ~0.3 KB + 1.5 KB (E2) | ~1.2 GB |
| T1 validation runs | ~7.9 k | ~57 KB (E1 diagnostics) | ~0.45 GB |
| T3 OP1 records | ~3.6 k | ~0.3 KB + 1.5 KB (element) | ~0.01 GB |
| T5 source observations | ~531 k (67.2/filing) | ~0.5 KB + 4.3 KB (E3) | ~2.5 GB |
| T6 members | ~555 k (70.2/filing) | ~0.25 KB + 1.6 KB (element) | ~1.0 GB |
| T7 member comparisons | ~29 k | ~0.25 KB + 0.4 KB (element) | ~0.02 GB |
| T4 economic facts | ≤ ~452 k (57.2/filing; fewer in steady state) | ~0.25 KB | ~0.11 GB |
| T13 records (first pass) | ~452 k | ~0.6 KB + 2.6 KB (E4) | ~1.45 GB |
| T14 inputs | ~531 k | ~0.2 KB + 0.85 KB (element) | ~0.56 GB |
| T15 cross-SO comparisons | ~87 k | ~0.3 KB + 0.55 KB (element) | ~0.07 GB |
| T16 batch results | ~452 k | ~0.1 KB | ~0.05 GB |
| T12 batches | ~290 per pass (issuers) | selection + results | ~0.1 GB |

- **Totals:** about **7.5 GB before indexes, 9–10 GB with them**, per full generation. That is about 0.95 MB per filing:
  - F6.2 §12's 0.5–0.6 MB;
  - the envelopes;
  - the element copies of §11.6, about 1.4 GB in all.
- **Growth:**
  - later reconciliation passes add only changed facts (C1, C6);
  - a new validation generation (for example issuer decisions for every filing, or a new F6 version) adds about 5.2 GB (T1–T3, T5–T7);
  - market data (about 0.54 GB/year) is separate.
- **Principle:** storage size is not a reason to discard structured evidence (F6.2 §11).

**Processing.**
- **Validation CPU.** The F6.3 corpus run takes about 0.1 s per filing to validate, so the backfill is about 15 min of CPU.
- **Inserts.** It then inserts about 3.8 M guarded rows, with the §11.6 checks at insert and at commit (each envelope parsed once). Of the order of one to two hours in all.
- **Partition passes.** A pass is bounded by the largest issuer, about 100 filings and 7k SOs, which is well within memory.

**Deliberately not done (no premature denormalisation):**
- **No partitioning:** under 10 M rows per table.
- **No materialized views:** "current" is a plain view. If profiling later shows a need, a materialized projection may be added. It must be rebuildable, refreshed only by the reconcile job, and never authoritative.
- **No duplicated inputs:** references only (§6.6).

**Indexes** are exactly those listed with each table: forward and reverse provenance, fact lookup by issuer/concept/period, record lookup by chain, state and annotation.
