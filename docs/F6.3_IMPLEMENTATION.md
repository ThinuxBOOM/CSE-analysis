# F6.3: Pure financial-truth domain layer

**Status:** implemented (uncommitted). Awaiting release-manager review.

**Baseline:** `40e15bc` (P3 frozen).

**Canonical design:** [`docs/F6.2_DESIGN.md`](F6.2_DESIGN.md). Where this note and the design differ, the design wins.

F6.3 turns the F5 and F6.1 outputs into admitted observations, economic-fact identities, source observations and reconciliation results:

```
F5 candidate → F6.1 validation (f6.validation.1, unchanged) → f6.admission.1 (with f6.op1.partition.1 and f6.inputs.1)
            → f6.identity.1 → source observation → f6.reconciliation.1 → single_source | corroborated | conflicting
```

**Boundary.** The layer is pure and deterministic:
- It reads no database, network, file, clock, environment, scheduler, PDF, Gemini output or market data. `tests/test_f63_determinism.py` enforces this statically.
- The same inputs and versions give byte-identical output and hashes, whatever the input order.
- It adds no migration, table, view or trigger. Persistence is F6.4.
- It edits no existing file.
- It uses F6.1 only through its public functions: `contexts_from_f5_result`, `validate_run`, `run_evidence`, `compare_values`, `arithmetic_group_key` and `canonical_json`.

## 2. How the pieces are used

```python
run  = inputs.f5_run_ref(f5_result, f5_run_id=..., recorded_at=...)
vr   = admission.validate_run(f5_result, f5_run=run, issuer_link=IssuerLinkDecision(...) or None,
                              uploaded_at=report_filings.uploaded_at, document=DocumentContext(...))
sos  = observations.build(vr)                                     # one SO per (validation run, ef_key)
cfg  = reconciliation.ReconciliationConfiguration(accepted_f3=..., accepted_f4=..., accepted_f5=...)
batch = reconciliation.reconcile(all_f5_runs_of_the_documents, all_sos, cfg)
```

**What each step produces:**
- **The validation run** holds, for every candidate:
  - the F6.1 input (`CandidateContext`) and the F6.1 output (`CandidateValidation`), both unchanged;
  - the admission, together with the identity and `ef_key` when admitted;
  - the F6.1 A1–A5 and sign diagnostics;
  - one OP1 record per statement column and concept that holds a section-derived row.
- **Source observations** keep each member's F5 value verbatim and F6.1's normalised value beside it.
- **The reconciliation batch** holds:
  - the run selection;
  - the excluded observations, each with its reason;
  - one result per `ef_key`.
- **Keys and hashes** are content-derived SHA-256 values:
  - the validation-run key;
  - the candidate-validation key;
  - `so_key`;
  - `configuration_id`;
  - every `input_hash` and `output_hash`.

## 3. Interpretations made while implementing

These points are not spelled out in the design. None of them selects a winner or changes a value.

1. **Agreement across SOs with several members is tested on every pair of observed values** (member-level V8). For single-member SOs this is exactly V8 on the SOs. It makes the fact interval the intersection of the SOs' own intervals, so it can never be empty. Comparing only each SO's representative could call a fact corroborated while a printed value disagrees, and could produce an empty interval. On the real corpus both readings give identical results.
2. **Ties at the finest precision with equal values** give that value. The first SO in canonical order (document SHA-256, then `so_key`) is cited. A nil fact cites its first SO the same way. The choice never affects the value.
3. **An OP1 term printed at several precisions but with one value** uses the finest half-unit, the strictest tolerance. A section-derived row that is not itself a term of a passing partition (for example an F5 `conflicting` row) is refused as `insufficient_evidence`.
4. **Admission reason codes:**
   - `validation_ineligible`
   - `normalization_not_admissible`
   - `issuer_link_not_supplied`
   - `issuer_link_not_evidenced:<status>`
   - `issuer_link_path_prefix_only`
   - `operations_section_derived_unvalidated:<outcome>`
   - `maturity_undetermined:<basis>`
   - `scope_unrecognised:<value>`
   - `identity_incomplete:<field>`

   Every rule is evaluated for every candidate. F6.1's own reasons stay in F6.1's result, and `admission.refusal_reasons()` gives the union.
5. **`f6.inputs.1`** uses the fixed Colombo offset UTC+05:30, as P2 does. It refuses instants before 2006-04-15, when Sri Lanka used other offsets, rather than guess.
6. **`audit_labels_differ`** requires two different *known* labels. `unknown` is the absence of a label, not a label. On the corpus, 48 corroborated facts pair a known label with `unknown`, and none pairs `audited` with `unaudited`.
7. **Document-type annotations:**
   - `differs_interim_vs_annual` reads F3's `underlying_type`, so an errata of an annual report counts as annual.
   - `differs_across_document_versions` reads F3's `document_type` (`errata_or_reissue`, `amendment`) on either side of a disagreeing pair.
   - `restated_comparative_present` is any member column carrying F5's `restated` flag.
   - `sign_only_difference` marks a disagreeing pair that would agree under F6.1's `compare_values` with one sign reversed. It is interpretation only; nothing is flipped.
8. **The SO role annotation** ("annotated if more than one", §5) is named `multiple_roles`.
9. **The reconciliation `input_hash`** also covers the cross-fact context: the filings per document and the other presentation currencies. Otherwise a new filing of the same document would change an annotation without changing the hash, and the append-on-change rule (§7) would drop it.
10. **One run per document.** The rule is the most recently recorded accepted run.
    - On an exact tie in `recorded_at`, the greater run id wins.
    - Several accepted runs of one document without `recorded_at` are refused.
    - Several validation runs of one selected F5 run are refused rather than chosen between; the design does not say which to use, for example after a new issuer decision.
11. **Out of scope for F6.3:**
    - The as-of cut (§9.2) is not implemented; the configuration has no cutoff.
    - The runtime fields are not produced: the validation run's `started_at` / `finished_at` / `recorded_at` / `code_revision` / `job_attempt_ref`, the SO's `recorded_at`, the fact's `first_recorded_at`, and the reconciliation `sequence` / `previous_record_id`.

    All of these belong to F6.4. The fields the as-of cut needs are preserved: F5 run `recorded_at`, the raw timestamp snapshot, the issuer decision's `decided_at`, and the F3 `classification_id`.

## 5. For F6.4

- **Store the content-derived keys and hashes** as they are. A database-generated `so_id` in the reconciliation `input_hash` would break reproducibility.
- **Decide which validation run to use** when an F5 run has several under the same versions. F6.3 refuses such input.
- **A new migration will trip a P3 test.** The frozen test `tests/test_p3_scheduler_unit.py::test_new_migrations_continue_after_0013_and_0006_stays_unused` asserts that `0014` is the last migration, so a new `0015` needs that test updated by an owner decision.
- **R-1 (§15.3) is still open.** It does not affect F6.3.
